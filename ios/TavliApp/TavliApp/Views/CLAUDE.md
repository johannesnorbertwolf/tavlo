# Views — SwiftUI rendering layer

SwiftUI views for the Caramel board. These own all drawing/aesthetics; pure geometry lives in
the `BoardGeometry` package (engine-free) and game logic in `TavliEngine`. Views depend on both;
neither depends on views.

**Full per-view detail (draw order, gestures, layout math, previews) is in
[`REFERENCE.md`](./REFERENCE.md)** — read it when implementing or modifying a view.

**Variants (#143).** The selected variant (`GameVariantSetting`, `AppSettings.swift`, key
`settings.variant`) drives new games; a session/record always carries its own variant, which
every view reads (`session.game.variant` / `record.variantID`). The variant is chosen in the
new-game sheet (#189); the start screen gates vs-AI play on `NewGameSetup.aiAvailable` and offers "Two players on this iPad" for any variant; saves
show their variant and are disabled when their vs-AI model is missing. Board views work in
`BoardLayout` **display slots** (engine 0…25 + bar slots 26/27 for Portes) — see `REFERENCE.md`.

**iPhone (#109).** Board screens (game, opening roll, review, drill) read their
`GeometryReader` into `ChromeLayout` (pure, in `BoardGeometry`, unit-tested) and branch on
`layout.mode`: compact portrait = board full safe width at the safe bottom, chrome above
(icon bar + "⋯" menu for Save/Resign/Leave/history/Settings/debug); compact landscape = board full
safe height, chrome in a rail. `ChromeType` sizes scale by 0.86 on a phone (set once in
`App.init`). No mascot on any layout (removed in #192). Per-screen detail in `REFERENCE.md` ("Compact (iPhone) layout").

## Conventions / gotchas

- **iPad stays pixel-identical.** Every iPhone change goes in an `if layout.isCompact` /
  `ChromeType.isCompact` branch; never retune a regular-mode constant for the phone.
  No `userInterfaceIdiom` layout checks (the only one names the device in copy).

- **Never hard-code a variant in a view.** Map engine positions through `BoardLayout`
  (`displayStacks`, `displaySlot(forSource:)`, `sourcePosition(forDisplaySlot:)`,
  `borneOffCount`) — Portes keeps bar checkers in the end stacks, so raw `points[0]/[25]`
  counts are wrong; Fevga Black wraps 24→1. Label evaluations through `EvalScale`.

- **No game logic in views.** Every view binds to `GameSession`'s published read-state and calls
  its intents; rendering/aesthetics only.
- **Pass a value-type board snapshot, not `[Point]`.** The engine mutates `Point` *reference*
  objects in place, so a `[Point]` is reference-identical across moves and SwiftUI skips the
  repaint (board freezes mid-game). `CheckersView`/`SourceRingView` take a `[[Color]]` snapshot
  (`points.map(\.pieces)`) so each committed move repaints.
- **Colors come from `CaramelPalette`** (defined in `BoardView.swift`, with `Color(hex:)`);
  engine→display name/color mapping is centralized in `ChromeTheme` (`GameView.swift`). Add new
  palette colors to `CaramelPalette`.
- **Dark mode (#191): every colour must adapt.** Declare tokens as `Color(light:dark:)` — the
  light value is the original hex (light mode must stay pixel-identical), the dark value comes
  from `design/dark-mode/themes.js` (C3 · Espresso + warm text, walnut board). No hard-coded
  `Color(hex:)`/`.white` in chrome: page = `ChromeKit.pageColor`, label on a solid accent =
  `ChromeKit.onAccent`, dimmed text = `inkSecondary` / `inkDim(x)`. Token tables in `REFERENCE.md`.
- **Localized display titles use `ChromeType.statsTitle` / `localizedWordmark`**, never a raw
  Cormorant font: Cormorant is Latin-only, and those fall back to the system serif for Greek
  (#225) and Persian (#185). Strings live in `Localizable.xcstrings` (de/nl/el/fa); see REFERENCE.md "Localization".
- **Chrome text sizes come from `ChromeType`** (`GameView.swift`, #92): fixed sizes one step
  above the system text styles, for older players. No hardcoded font sizes in chrome views;
  board/dice/checker sizing is geometry-scaled and exempt.
- **Buttons and cards come from `ChromeKit`** (#101): style buttons with `ChromeButton`
  roles and surfaces with `.chromeCard()` — no bespoke gradients, hairline borders, or
  sub-44pt tap targets in chrome views. Dimmed text uses `ChromeKit.inkSecondary`, nothing
  lower.
- **All metrics scale by `geo.scale`** off the 900-unit design reference, so any board size
  reproduces the reference 1:1. Each view rebuilds an identical `BoardGeometry` so layers register.
- **Persisted settings (#77) live in `AppSettings.swift`** (one level up, the target root): the
  option enums + the `SettingsKey` UserDefaults keys + static accessors for non-view contexts.
  Views bind via `@AppStorage` (keep each declaration's default equal to the matching accessor —
  e.g. Play as = White, Auto-roll = on, AI level = `AILevel.max` (8), in every view that declares them). The match-length
  toggles (#145, `MatchLengthSetting`; `matchLength` for vs-AI, `onlineMatchLength` for online) live
  there too and default to **best-of-three** (chosen in the new-game sheet / lobby, not the Settings sheet).
  Retired values are rewritten once at launch (`AppSettings.migrateLegacySettings()` from `App.init`, #189):
  the strength slider → nearest level, Play as `ask` → `random`.
- **Right-to-left (#185, Persian): board views pin LTR; chrome mirrors; isolate notation.** The board, checkers,
  dice, highlights, animations and the review chart never mirror (`.boardLayoutDirection()` on `PlayableBoardView`,
  the review/drill/opening-roll board stacks, `DieFace`, `WinProbabilityChart`); everything else mirrors by itself.
  Back/forward glyphs use `DirectionalSymbol`, running scores `ScoreLineText`, move notation is LTR-isolated in
  `MoveNotationText`, pre-formatted numbers go through `ChromeDigits`. Every hook must be a no-op in LTR (iPad
  pixel-identical in en/de/nl). Detail + Persian glossary in `REFERENCE.md` ("Right-to-left / Persian").
- **Handicaps (#148) are invisible when off.** Every hook (`HandicapTagButton`, the
  `ControlsView` actions row, the review note, the hint overlay in `PlayableBoardView`, the
  My Record block) renders only when `session.handicap` / `record.handicap` / handicap stats
  exist; the off path keeps the exact pre-#148 view tree. New handicap UI goes in the
  `Handicap*.swift` files; `HandicapPreferences` (`HandicapSettings.swift`) is the only
  settings key (`settings.handicap`, JSON).
